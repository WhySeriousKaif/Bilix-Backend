# Billix POS: Engineering Problems, Decisions, and Interview Notes

This document records important problems encountered while building and deploying Billix POS, how they were diagnosed, how they were fixed, and how the design should evolve for production. It contains no credentials or production secrets.

## 1. How should Copilot authentication work for many users and roles?

### Interview question

How did you design a GenAI assistant that respects multi-tenant access for cashiers, branch managers, store administrators, and super administrators?

### Temporary implementation and its limitation

The first deployed version configured `SPRING_API_TOKEN` in the AI service. It was a JWT obtained from one manager account. FastAPI used that token whenever an AI tool called a protected Spring endpoint.

This was acceptable only as a short-lived deployment proof. It has serious production limitations:

- Every AI tool call impersonates the same manager.
- The token expires and must be replaced manually.
- A cashier, store admin, and super admin do not have the same permissions or data scope.
- Multiple stores and branches cannot safely share one identity.
- Revoking or changing that manager account can break Copilot for everyone.
- Storing a user JWT as a service environment variable confuses user identity with service identity.

### Implemented solution

Use two separate identities:

1. **Service identity**: Spring authenticates to FastAPI with `AI_SERVICE_API_KEY`.
2. **User identity**: every Copilot request carries the JWT of the currently authenticated user for that request only.

Implemented request flow:

```text
Browser
  -> user JWT
Spring Boot API
  -> validates the user and requested branch/store scope
  -> forwards the current Authorization header over HTTPS
FastAPI assistant
  -> stores the header in a Python ContextVar for this async request only
  -> sends the same header when invoking an approved Spring read tool
  -> clears the ContextVar in a finally block
Spring protected endpoints
  -> validate the JWT again through Spring Security
  -> enforce the user's role and store/branch access
PostgreSQL
```

The previous `SPRING_API_TOKEN` setting was removed from Python settings, the example environment file, and `render.yaml`. Managers no longer require individual environment variables. Each signed-in user automatically uses their own authenticated identity.

Python `ContextVar` was chosen instead of a global variable because FastAPI handles concurrent asynchronous requests. A global token could allow one user's token to be read by another request. A context variable isolates the value to the current execution context, and the `finally` block guarantees cleanup even when the model or a tool fails.

### Authorization boundaries

Spring derives and enforces access from the authenticated user. It does not trust the LLM to decide authorization:

- The controller verifies that a branch manager can access the requested branch before calling AI.
- Store administrators receive only data allowed by their store-level Spring authorization.
- Super administrators use the system assistant endpoint, which first requires the administrator role.
- Python cannot bypass Spring because its tool calls return through JWT-protected Spring endpoints.
- `AI_SERVICE_API_KEY` still protects FastAPI from direct unauthenticated callers, but it never represents a user.

### Verification

- Added a Spring service test proving that the current `Authorization` header is forwarded to FastAPI.
- Added a controller test proving that the same authenticated header reaches the AI service layer.
- Added a FastAPI test proving that assistant chat rejects a missing user token with HTTP 401.
- Added a Python tool test proving that Spring tool calls carry the current request's user token.
- Spring test suite: **42 passed**.
- Python AI test suite: **38 passed**.

### Future hardening

The implemented forwarding design is intentionally simple and is appropriate for the current project. A larger production platform can later replace the forwarded login token with a 2–5 minute delegated token containing narrower AI permissions, for example:

```json
{
  "sub": "authenticated-user-id",
  "aud": "billix-ai",
  "role": "ROLE_BRANCH_MANAGER",
  "storeId": 12,
  "branchId": 31,
  "permissions": ["products:read", "inventory:read", "dashboard:read"],
  "exp": "2-5 minutes from issue time"
}
```

Spring must derive these claims from its authenticated `SecurityContext`. It must never trust a store ID, branch ID, or role supplied by the browser or generated by the language model.

### Role-based scope

- **Cashier**: own branch products, inventory, customers, own shift, and permitted orders.
- **Branch Manager**: all operational data for the assigned branch.
- **Store Admin**: all branches, inventory, orders, staff, and analytics belonging to the assigned store.
- **Super Admin**: system-wide summaries and explicitly approved administrative data.

The LLM can decide which read-only tool is useful, but Spring remains the authorization authority. The model cannot expand the user's scope.

### Security requirements

- Keep `AI_SERVICE_API_KEY` separate from user JWTs.
- Use short token expiry and an `aud=billix-ai` audience restriction.
- Prefer allow-listed read-only AI tool endpoints.
- Derive tenant scope on the server.
- Record user ID, tool name, scope, time, and result status in an audit log.
- Apply rate limits and tool timeouts.
- Never send database credentials or payment secrets to the model.
- Require explicit confirmation for any future write tool.

### Strong interview answer

> The first demo used a static manager JWT, which made every AI tool impersonate one manager and would not scale across users or roles. I separated service authentication from user authorization. Spring still authenticates to FastAPI using a service key, while the logged-in user's JWT is forwarded only for the current chat request. FastAPI isolates it with a ContextVar, uses it for approved Spring tool calls, and removes it in a finally block. Spring Security revalidates every call and enforces the user's branch, store, and role scope, so the model can choose a tool but cannot expand data access. I also added regression tests and removed the static token from deployment configuration.

## 2. Why did paginated data work locally but fail on PostgreSQL?

### Symptoms

- Cashier product list displayed `Failed to load products`.
- Branch orders and refunds displayed no data.
- Super Admin dashboard showed zero values and `An unexpected error occurred`.
- Browser Network tools showed HTTP 500 responses from several `/paged` endpoints.
- H2-based local tests passed, while Render PostgreSQL failed.

### Root cause

Several JPQL queries used a pattern such as:

```sql
(:search IS NULL OR LOWER(entity.name) LIKE ...)
```

When optional parameters were `NULL`, PostgreSQL could not always infer their SQL types. H2 was more permissive, which hid the defect locally. The same query style appeared in products, orders, refunds, and system-wide sales, so multiple roles failed at once.

A second issue affected order and refund mapping: DTO conversion accessed lazy relationships, including order items and refund items, after the repository transaction had ended. That could produce a `LazyInitializationException` in production.

### Fix

- Added `JpaSpecificationExecutor` to the product, order, and refund repositories.
- Built predicates dynamically, adding a condition only when the corresponding filter has a value.
- Removed dependence on nullable filter parameters in the paginated production path.
- Added read-only transactional boundaries around paged order and refund retrieval so lazy data is mapped while the persistence context is active.
- Preserved server-side branch/store access checks before querying.
- Ran the complete Spring test suite: 42 tests passed.

### Why the fix is better

Specifications produce typed predicates and avoid a large number of query variants. They support optional filters without asking the database to interpret untyped `NULL` parameters, and they remain composable as new filters are added.

### Interview answer

> The issue appeared only after moving from H2 to PostgreSQL. Multiple paginated JPQL queries used nullable parameters, and PostgreSQL's stricter type inference rejected some null-bound expressions. Order/refund mapping also crossed a lazy-loading boundary. I replaced the nullable-query pattern with composable JPA Specifications and added read-only transactional mapping boundaries. That fixed cashier, manager, and super-admin pages through one shared backend correction.

### Prevention

- Run repository integration tests with PostgreSQL through Testcontainers instead of relying only on H2.
- Test every endpoint with filters both absent and present.
- Log the original server exception with a request correlation ID.
- Add API smoke tests for each role after deployment.

## 3. Why did the backend fail to connect to Render PostgreSQL?

### Symptom

Spring failed during startup with `UnknownHostException` for a `dpg-...-a` hostname. Tomcat never became healthy.

### Root cause

The backend still contained an internal connection URL belonging to an unavailable or replaced Render PostgreSQL resource. An environment variable can remain present even after the resource it references is gone.

### Fix

- Created a new PostgreSQL resource in the same Render workspace and Oregon region as the backend.
- Replaced the datasource URL, username, and password with the new resource's values.
- Kept the internal URL because both services were in the same workspace and region.
- Redeployed and verified `HikariPool` connected before Tomcat became live.

### Lesson

Configuration presence does not prove that the referenced infrastructure exists. Always verify the resource lifecycle, region, workspace, DNS reachability, and connection health.

## 4. Why did the AI Docker build fail on `README.md`?

### Symptom

Docker failed at:

```dockerfile
COPY pyproject.toml README.md ./
```

with `README.md: not found`.

### Root cause

The local README existed as an empty/untracked file and was excluded by local Git rules. Render builds only from committed repository content.

### Fix

- Removed the unnecessary README copy instruction.
- Removed the missing README reference from Python package metadata.
- Verified the Python wheel build locally.

### Lesson

Test from the committed Git tree or a clean Docker context, not from assumptions about files present on one workstation.

## 5. Why did Python package installation discover unrelated folders?

### Symptom

`pip install .` failed because setuptools found multiple top-level packages such as `app`, `rag`, `data`, `notebooks`, and `recommendation`.

### Root cause

The project used a flat directory layout without explicit package-discovery rules.

### Fix

Configured setuptools to package only `app*` and declared an explicit build backend in `pyproject.toml`.

### Lesson

Deployment packaging should explicitly declare what belongs in the runtime artifact. Incidental repository directories must not be auto-discovered as application packages.

## 6. Why did the AI container fail with `Policy directory does not exist`?

### Symptom

The image built successfully, but the container exited while creating the policy vector index because `data/policies` was missing.

### Root cause

The policy Markdown files existed locally but were excluded by a local `*.md` Git rule. Docker's `COPY data data` cannot copy files that Render never received from Git.

### Fix

- Explicitly added and committed the three policy documents.
- Redeployed the AI service.
- Verified the generated policy index and `/assistant/health` response.

### Lesson

AI systems depend on prompts, policies, models, and indexes as deployable artifacts. Validate that every required runtime artifact is tracked or generated deterministically during deployment.

## 7. Why was the AI backend healthy but the Copilot UI missing?

### Symptom

FastAPI and Spring were deployed, but the Vercel application showed no Copilot navigation item or chat widget.

### Root cause

The frontend AI implementation was committed to `codex-production-hardening-ui`, while Vercel deployed `main`.

### Fix

- Built the frontend production bundle locally.
- Committed the assistant routes, page, and widget to `main`.
- Pushed `main` and waited for Vercel to deploy the new commit.

### Lesson

Backend readiness and frontend feature availability are independent. Always verify the exact Git commit deployed by every platform.

## 8. Why did the AI root URL say `Invalid AI service key`?

### Symptom

Opening the AI service root directly in a browser returned HTTP 401 with `Invalid AI service key`, while `/assistant/health` returned `UP`.

### Explanation

This was expected. Business endpoints were protected with a service-to-service key, while health endpoints were intentionally public for Render health checks. A browser request did not include the required `X-AI-Service-Key` header.

### Lesson

A protected root endpoint is not evidence of a failed service. Health checks, authentication checks, and functional API checks are different tests.

## 9. Why did Copilot show `temporarily unavailable`?

### Symptom

The assistant UI loaded, but Spring returned its generic unavailable response.

### Likely integration causes

- Spring and FastAPI had different `AI_SERVICE_API_KEY` values.
- `AI_SERVICE_BASE_URL` pointed to the wrong service.
- The static `SPRING_API_TOKEN` had expired.
- A free Render service was waking from a cold start.
- FastAPI returned a downstream OpenAI or Spring tool error.

### Diagnostic approach

1. Verify `/assistant/health` reports that the assistant and policy index are loaded.
2. Inspect the Spring log line beginning with `AI assistant request failed`.
3. Inspect FastAPI logs using the same timestamp.
4. Verify that the service key is identical without quotes or whitespace.
5. Replace the static user token with request-scoped or delegated authentication.

### Lesson

Do not collapse all downstream failures into an untraceable message. Return a safe error to users, but log a correlation ID, downstream service, status code, latency, and failure category for operators.

## 10. Recommended production improvements

- Replace `SPRING_API_TOKEN` with short-lived delegated user tokens.
- Use PostgreSQL Testcontainers in CI.
- Add Flyway or Liquibase migrations and change production Hibernate DDL from `update` to `validate`.
- Add structured logs and request correlation IDs across Vercel, Spring, and FastAPI.
- Add role-based end-to-end smoke tests.
- Add retries only for safe transient calls, with timeouts and circuit breaking.
- Store secrets only in deployment secret stores and rotate any secret exposed in screenshots or chat.
- Add AI audit logs and evaluation datasets for tool selection, authorization, groundedness, and answer quality.
- Keep AI tools read-only by default; require confirmation and stronger authorization for writes.

## Short project summary for interviews

> Billix is a multi-role POS platform with a React frontend, Spring Boot domain API, PostgreSQL, and a FastAPI GenAI/recommendation service. The assistant uses tool calling and policy retrieval while Spring remains the authorization and tenant-isolation boundary. During deployment I solved cross-database query behavior, lazy-loading boundaries, container packaging, missing RAG artifacts, multi-repository branch deployment, service authentication, and Render networking. The next security step is replacing the proof-of-concept static manager token with short-lived delegated user authorization.
